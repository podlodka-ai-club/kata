# Две находки, которые меняют методику

Обе получены прогоном, а не рассуждением. Обе бьют по тому, как в [`../evals/README.md`](../evals/README.md) устроены скрытые проверки.

---

## 1. Тесты из эталонного PR дискриминируют не всегда

Соблазнительная идея «берём PR, его тесты и есть скрытая проверка» верна не для всех PR. Проверка простая: прогнать тесты из коммита на **родительском** коммите (должны падать) и на самом коммите (должны проходить).

Прогнал 23 кандидата. **Четыре отбраковались — их тесты зелёные и до изменения:**

| Коммит | Почему не годится |
| --- | --- |
| `e52a887e3` publish all mealplan events | тест лишь добавляет два поля в генератор фикстуры, pydantic их проглатывает. 5 passed на родителе |
| `d3436a5ca` add label notifier | то же самое: тесты нотификаторов собираются генератором фикстуры |
| `ea06e2102` lazy module loading | 5 passed на родителе |
| `b096b6537` fix pytest warnings | 71 passed на родителе |

Обиднее всего первая: это была самая красивая задача на конвенцию событий — «новый тип события ⇒ поле у подписчика ⇒ миграция», конвенция даже записана в докстринге `EventTypes`. Без проверки мы бы считали её сильной задачей и мерили пустоту.

Обратите внимание на закономерность: **обе отбракованные событийные задачи провалились по одной и той же причине.** Тесты нотификаторов в mealie параметризованы генератором фикстуры, который молча принимает новые поля. Это свойство репозитория, а не случайность, — значит срез `event-graph` в mealie автоматически не измеряется в принципе, под него нужен `llm-judge`.

**Вывод для раннера:** валидация дискриминации — обязательный шаг подготовки каждой задачи, а не разовая проверка методики. Команда:

```bash
git checkout <base_commit>
git checkout <solution_commit> -- <тест-файлы из коммита>
pytest <тест-файлы>        # должно ПАДАТЬ
git checkout <solution_commit>
pytest <тест-файлы>        # должно ПРОХОДИТЬ
```

## 2. Классы A и B: раскрытие контракта — это утечка того самого факта

Задачи, которые дискриминируют, падают на родителе **двумя разными способами**, и разница принципиальная.

**Класс A — поведенческий.** Тесты падают ассертами: все имена уже существуют, меняется поведение. Формулировка задачи пишется по-человечески, ничего раскрывать не нужно. **Тесты эталонного PR годятся как `hidden-test` напрямую.**

**Класс B — контрактный.** Тесты падают на этапе сбора, потому что импортируют модули, которых на базовом коммите ещё нет. И вот здесь ловушка:

> Чтобы тест хотя бы собрался, в постановку придётся написать «положи это в `mealie/pkgs/safehttp`». Но «исходящий HTTP централизован в `mealie/pkgs`» — это **ровно тот архитектурный факт, который мы и проверяем**. Раскрыв контракт, мы подсказываем ответ обоим прогонам и убиваем дельту.

Это тот же класс ошибки, что уже описан в ловушках эвалов («формулировка задачи не должна протекать»), просто он приезжает не через issue, а через требования теста.

**Вывод:** для класса B тесты эталонного PR как `hidden-test` не годятся. Проверки пишем в двух других видах из нашего же чеклиста:

- `grep` — детерминированный паттерн по диффу: «новый HTTP-клиент не создаётся в `services/scraper/`»;
- `llm-judge` — судья с эталонным PR как reference: «расширен существующий централизованный HTTP-слой, а не написан свой».

Так проверка меряет именно архитектурное решение, а постановка остаётся честной.

## Как это ложится на состав датасета

| Класс | Скрытая проверка | Роль в эвале |
| --- | --- | --- |
| **A** | тесты эталонного PR, валидированные на дискриминацию | **ядро**: детерминированно, без судьи, без споров |
| **B** | `grep` + `llm-judge` по эталонному диффу | расширение: сильнее по архитектуре, но требует судью |

Отбор задач класса A автоматизируется: коммит не добавляет новых модулей под `mealie/` (миграции не считаются), не добавляет новых тест-файлов, трогает ≥2 компонента и имеет тесты. После 05.05.2026 таких в mealie **11 штук** — на текущий набор хватает с запасом.
