# kata — системный дизайн как память агента

Хакатон агентской памяти. Гипотеза, которую проверяем:

> **Память технических фактов о системном дизайне проекта (в xmemory) улучшает работу
> кодового агента** — меньше токенов и переделок, меньше архитектурных ошибок.

Инвертируем задачу системного анализа: не проектируем схему знаний заранее и не предсказываем
будущее — агент **реверс-инжинирит технические факты из уже существующего кода**, человек только
выбирает нужные срезы и ревьюит сомнительное. Дальше эта память живёт рядом с проектом,
актуализируется при каждой задаче и (гипотеза) делает будущие реализации качественнее и дешевле.

Наша работа = **хороший скилл + честные эвалы**. Всё остальное делает фронтир-модель на вайбе.

## Happy path

1. Пользователь вызывает скилл `/tech-facts`.
2. Агент разведывает репозиторий и поднимает **локальный UI** (`localhost:4747`): лендинг-picker
   со срезами системного дизайна, которые реально есть в этом проекте.
3. Пользователь отмечает нужные срезы прямо на странице — решение уезжает агенту само
   (блокирующий `await`, без копипасты JSON в чат).
4. Агент сам проектирует схему под выбранные срезы — **тип объекта на срез** со своими полями и
   связями, а не общая таблица заметок, — извлекает срезы параллельно и пишет факты в **xmemory**;
   уверенное подтверждает сам, сомнительное отдаёт человеку на ревью.
5. Дальше агенту дают поток задач: перед задачей SessionStart-хук **читает** факты в контекст,
   после — Stop-хук возвращает агента на шаг **актуализации** памяти
   ([контракт](skills/tech-facts/usage-contract.md), [механика](dataset/README.md)).
6. Эвал сравнивает три хронологических потока: **без памяти**, **read/write memory** и
   **read/write memory + evolution checkpoint**.
7. После `a3` в третьем потоке отдельная curator-session дедуплицирует facts, разрешает
   противоречия, помечает stale/superseded и разбирает предложения эволюции схемы; coding task
   она не решает.

## Текущий исследовательский протокол

Первый seed из PR #8 сохранён как архивный **naive full-snapshot negative control**: read-only
memory-on получал один полный dump. Новый primary protocol реализует три отдельных stream и не
переписывает старые результаты. Сначала запускаются бесплатные fake/null/oracle gates, затем canary
`a3 → a6` одним seed. Полная матрица `6 tasks × 3 modes × 2 repeats` разрешена только после зелёного
canary; отчёт показывает оба seed и median/range, а не трактует один seed каузально.

В memory modes порядок семантически значим:
`a1 → a2 → a3 → [evolve только в третьем режиме] → a4 → a5 → a6`. Каждая задача — новая
coding-session и независимый code workspace. Перед каждой memory-сессией создаётся новый xmemory
child: a1 клонируется из read-only C0 template, следующая сессия — из предыдущего child. Поэтому
memory state переживает рестарт только через xmemory, а mutable instance никогда не делится между
экспериментальными ячейками.
После подтверждённого clone/read boundary runner удаляет только предыдущий child своего stream,
а после stream — его tail. C0 остаётся неизменяемым; локальный lineage сохраняет IDs, hashes и
delete receipts, поэтому ограниченная cloud-retention не превращается в скрытый перенос состояния.

### Что честно не закрыто

1. **Шаг «оценил результат».** В контракт использования заведено: результат сборки и тестов
   прогона — вход для `gotcha`-фактов. На потоке задач это не проверено, механика замыкается
   в раннере [`dataset/`](dataset/).
2. **Источник уроков.** ТЗ просит агента, который учится **на своих результатах**; у нас основной
   источник фактов — реверс-инжиниринг кода. Уроки из собственной работы — это `gotcha`-факты
   из U3, и это та часть, которую стоит усиливать.
3. **Фокус ТЗ — «механизмы памяти и самоулучшения».** State machine и curator checkpoint
   реализованы и проверены cloud-only full r2; фактическая модельная дельта остаётся неоценимой
   из-за отсутствия полностью paired eligible строк между тремя режимами.
4. **Эвал «полезен ли урок».** Нужно решить, делаем ли мини-проверку урока перед его активацией,
   или честно говорим, что этот блок не брали.

### Номинация xmemory

| Критерий | Как ложится |
| --- | --- |
| Значимый цикл write → read и durability | Факты пишутся на извлечении и после каждой задачи, читаются перед следующей — между сессиями, агентами и процессами; вручную контекст не переносится |
| Схема под задачу | Агент проектирует схему сам под выбранные срезы и репозиторий: тип объекта на срез, предметные поля и связи на сущности, плюс связи `Task ↔ Fact`. Не мешок текста и не одна таблица с полем «тип» |
| xmemory как часть продукта | Без памяти основной сценарий не работает: весь `memory-on` держится на чтении фактов из xmemory |
| Наглядность результата | Сайт-эксплорер над памятью + цепочка `Task → Fact` обходом графа: видно, что записано, что уехало в задачу и что изменилось |

## Глоссарий

- **тип факта** — описание элемента системного дизайна (внешние интеграции, зависимости модулей).
- **факт** — собираемая единица: «сервис А ходит в сервис Б», «модуль С зависит от модуля Д».
- **срез** — набор типов фактов, который человек выбирает в picker'е.
